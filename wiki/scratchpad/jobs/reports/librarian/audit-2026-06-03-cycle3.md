### 2. MOP phantom HITS nodes — 3 cycles running, no resolution

`wiki_hits_analysis` consistently shows two authority nodes for MOP:
- `[[maximum-occupancy-principle]]` 0.0130 (bare slug)
- `[[concepts/maximum-occupancy-principle]]` 0.0105 (prefixed)

The MOP page itself (`wiki/concepts/maximum-occupancy-principle.md`) has **zero self-references** to either form. The phantom is generated by 50+ external pages that link to `[[maximum-occupancy-principle]]` (bare), with only 3 pages linking to the prefixed form. The HITS algorithm in the MCP server appears to track link targets as text strings rather than resolved paths, so the bare-slug and prefixed-slug forms create separate authority nodes even though they resolve to the same file.

**Cycle 2 carryover prediction: "phantom should self-resolve next cycle" — VERIFIED FALSE.** This is a server-side HITS algorithm issue, not a file-system issue. The phantom will persist as long as external pages link to the bare slug.

**Possible fixes (none attempted in this cycle):**
- Bulk-rewrite external links from `[[maximum-occupancy-principle]]` to `[[concepts/maximum-occupancy-principle]]` — high-effort, touches 50+ files
- Update HITS algorithm in MCP server to resolve Obsidian paths — server change, not librarian scope
- Accept the phantom as a known limitation and document it

**Recommendation:** document as known limitation; do not rewrite external links (per skill: orphan count re-verifies every cycle, but a mass-link-rewrite is not in the librarian's direct-action scope).
